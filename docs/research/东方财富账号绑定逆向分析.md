# 东方财富账号与自选股同步：逆向分析

目的：评估“把东方财富登录与 FinScope 账号绑定，自选股实时同步”的可行做法。
范围：只读分析东财网页前端公开脚本，并对公开接口做无登录探测。没有登录、没有读取任何用户 cookie、没有触碰密码相关逻辑。
分析日期：2026-10-18。样本脚本保存在工作区外的 `d:\finscrope\.re\eastmoney\`（不入库）。

> 说明：这些都是东财网页自用的非公开接口，没有对外承诺。接口随时可能改版，下面每一条都标了证据来源和是否亲手验证过。

## 1. 结论摘要

| 问题 | 结论 | 把握 |
| --- | --- | --- |
| 登录态是什么 | 浏览器里的三个 cookie：`ut`、`ct`、`uidal`（另有 `pi`），域为 `.eastmoney.com`。`uidal` 前 16 位是用户 id，其余是昵称 | 读脚本得出，高 |
| 自选股读写靠什么鉴权 | 只靠上述 cookie。`webouter` 没带登录态时返回 `CUToken 为空` | 亲手验证，高 |
| 能否不借助浏览器、由服务端调用 | 能。myfavor 不带 `cb` 直接返回 JSON，匿名接口也能直连 | 亲手验证，高 |
| 能否做“扫码绑定” | 能起码到“生成二维码、等待扫码”这一步。扫码成功后 cookie 怎么下发还没亲眼见过 | 前半段已验证，后半段**未验证** |
| 能否做“实时”同步 | 自选股本身没有推送，只有轮询；行情有 SSE 推送 | 读脚本得出，高 |
| 是否要保存密码 | 不要。密码登录是 RSA 加密后提交，且带验证码，不建议自己实现 | 读脚本得出 |

## 2. 登录态

`quote.eastmoney.com/zixuan/build/index.js` 的用户模块：

```js
user.get = () => cookie.ut && cookie.ct && cookie.uidal
  ? { id: uidal.substring(0, 16), nick: uidal.substring(16) }
  : null
user.logOut = () => 清空 pi / ct / ut / uidal（domain=eastmoney.com）
```

- 已登录：请求 `https://myfavor.eastmoney.com/v4/webouter/...`，参数只有 `appkey`。
- 未登录：请求 `.../v4/anonymwebouter/...`，参数多一个 `bid`（匿名设备 id，来自 cookie `qgqp_b_id`）。
- `appkey` 是页面里写死的一个固定值（`index.js` 内），不是用户密钥。

## 3. 自选股接口（myfavor v4）

基址 `https://myfavor.eastmoney.com/v4/webouter/`，公共参数 `appkey`。页面用 JSONP（`cb=`）调用，服务端可以不带 `cb` 直接拿 JSON。响应统一是 `{state, message, data}`，`state == 0` 成功。

| 接口 | 用途 | 参数 |
| --- | --- | --- |
| `ggdefstkindexinfos` | 分组列表 | `data.ginfolist[{gid, gname}]`，`data.webindex` 里是自定义排序 |
| `gstkinfos` | 某分组成员 | `g=<gid>`；成员 `security="市场$代码$id"`，另有 `price`、`updatetime`、`note`、`star` |
| `ag` | 新建分组 | `gn=<名称>` |
| `mg` | 改分组名 | `g`、`gn` |
| `dg` | 删分组 | `g` |
| `asz` | 加入默认分组 | `sc=<市场$代码>`（还有对应的指定分组加入接口，本次没抓全） |
| `ds` | 从分组删除一只 | `g`、`sc` |
| `dslot` | 批量删除 | `g`、`scs`；超过 3500 字符改 POST，body 为 JSON |
| `ms` | 批量移动 | `g1`（源）、`g`（目标）、`scs`；同样超长改 POST |
| `ss` | 调整顺序 | `g`、`sc`、`sc1`、`sc2` |
| `has` / `hcs` | 置顶 / 取消置顶 | `g`、`sc` |
| `bs` | 持仓备注 | `sc`、`g`、`c/p/m/z/y/x/h/r/b` |
| `usindex` | 自定义指数栏 | `index` |

细节：

- 证券标识在接口里用 `$` 连接（`1$600519`），页面内部用 `.`（`1.600519`）。
- 只要能列出分组和成员，就能还原东财自选的全部内容，这也是我们之前“按分组全存”用的接口。
- 备用域名：页面有“降级开关”（`myfavor.eastmoney.com/v4/state.html`），异常时改用 `myfavor1.eastmoney.com`。

亲手验证：

- 匿名分组接口带无效 `bid`：`{"state":-12,"message":"BID解析失败"}`。
- 登录接口不带 cookie：`{"state":-2,"message":"CUToken 为空"}`。
- 两者都是 HTTP 200 + `application/json`，服务端直连可用。

## 4. 扫码登录流程

登录页 `passport2.eastmoney.com/pub/login` 把表单放在 iframe：`exaccount2.eastmoney.com/home/login4?request=…`。
`request` 是一段 JSON：回调页 `agentPageUrl`（`passport2.../pub/LoginAgent`）、成功后跳转地址、`domainName`/`deviceType`/`productType`/`version`。

扫码登录（来自 `NewLogin4.js`，并已逐步实测）：

1. `GET /home/login4?request=…` 取页面，里面有隐藏域 `__RequestVerificationToken`（ASP.NET 防伪令牌）和对应的防伪 cookie。
2. `GET /jsonapi/GenerateQrCode?rnd=<随机数>` 返回 PNG（实测约 1.8 KB，`Cache-Control: private`）。会话靠 cookie `_qct`、`_qcu`（实测下发，有效期约 90 天），这一步**不需要**防伪令牌，服务端直连即可。
3. 每秒 `POST /JsonAPI/GetQrCodeLoginStatus` 轮询。
   - 必须带防伪令牌：请求头 `RequestVerificationToken: <令牌>` 且 `X-Requested-With: XMLHttpRequest`；或者把 `__RequestVerificationToken` 放进表单 body。只带令牌头而没有这些，会得到 500 “anti-forgery field not present”。
   - 还要带 `domainName`、`deviceType`、`productType`、`version` 四个头，值取自 `request.data`。
   - 响应：`{rc:false, errorcode:40, error:"未获取到用户"}` = 还在等扫码（实测）；`errorcode:20` = 二维码失效（读脚本）；`rc:true` 且 `result` 有内容 = 登录成功（读脚本）。
4. 成功后前端把 `result` 交给 LoginAgent 页面执行 `LoginCallBack`，再跳回 `backurl`。LoginAgent 只执行回调，脚本里没有写 cookie 的代码，所以 **`ct`/`ut`/`uidal` 很可能是 `GetQrCodeLoginStatus` 响应的 `Set-Cookie`（域 `.eastmoney.com`）**。这是推断，需要一次真实扫码确认。

登录页其余入口：手机验证码（`SendActiveCodeForLogin3`、`MobileLoginByActiveCode`）、微信/QQ/微博第三方登录、账号密码（`Login3`，密码用 JSEncrypt RSA 加密，并带滑块验证码）。

## 5. 行情实时性

- 自选页的实时行情走 SSE：`https://push2.eastmoney.com/api/qt/ulist/sse?secids=…&fields=…&ut=<公开 ut>`，`EventSource` 且 `withCredentials: true`。我们现在服务端用的 `ulist.np/get` 是同一族的轮询版。
- 自选股列表本身没有推送通道：页面每次进入时取一次，之后靠用户操作触发接口。所以“实时更新自选股”在东财侧只能做成**轮询对比**。

## 6. 对 FinScope 的方案

不碰密码，只做扫码绑定 + 服务端轮询同步：

1. 用户在“自选研究”点“绑定东方财富”，后端按第 4 节第 1、2 步取二维码，前端展示。
2. 前端轮询我们自己的状态接口，后端代为轮询东财；成功后取下 `ut`、`ct`、`uidal`、`pi`，加密落库（只存这几个，不存手机号、不存密码），记录东财 uid 与昵称。
3. 同步任务用这组 cookie 调 `ggdefstkindexinfos` / `gstkinfos`，按“东财分组名 → 本系统分组名”对齐，成员用 secid 存（已有“外部标的”结构，板块/美股/指数/ETF 都不丢）。
4. 间隔：页面打开时 30–60 秒一次，后台 5–10 分钟一次；用分组成员列表的哈希判断有没有变化，没变不写库。限流或失败时退避，不要连续重试。
5. 方向：先做**东财 → 本系统单向同步**，本系统里手动加的标的不会被覆盖删除。反向写回（`asz`/`ds`/`ms` 等）技术上可行，但会改用户东财账号里的数据，建议单独评估再做。
6. cookie 失效（接口返回 `CUToken` 相关错误）时把绑定标成“需重新扫码”，不要静默失败。

## 7. 风险与边界

- 这些接口未公开承诺，东财改版或加风控会让同步失效；实现里要把解析和错误分类集中在一个 provider 里，失败可读（“东财登录已失效，请重新扫码”），并且不影响本系统已存数据。
- `ut`/`ct` 等同于账号登录凭证：必须加密存储（密钥走现有的密钥配置，不入库不入日志）、只给本人使用、提供“解除绑定”并立即删除。
- 高频调用会触发东财限流（本次本机直连 `push2` 已出现连接被断开的现象）；同步要有最小间隔和退避。
- 使用条款层面：只对**用户本人账号**、由用户本人扫码授权后读取，不做任何绕过验证码、批量账号或代登录。

## 8. 还没验证、需要一次真实扫码的点

1. 扫码成功时 `GetQrCodeLoginStatus` 的 `Set-Cookie` 具体是哪些，域和有效期是多少。
2. 服务端带这组 cookie 调 `webouter/ggdefstkindexinfos` 是否直接成功（是否还校验 `Referer`/`Origin`/IP）。
3. cookie 的实际存活时长，以及失效时接口返回的 `state`/`message`。

做法：由你用东财 App 扫一次后端生成的二维码，我只记录响应结构和 cookie 名称（不记录值），验证完立即退出该会话。
